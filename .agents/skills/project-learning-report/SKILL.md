# 项目学习报告

把一次项目工作写成可以自学的材料。读完后，用户应能说清楚改动解决了什么问题，知道去哪里读代码，并能亲自核对一个结果。

## 确定范围和深度

- 用户把任务和报告一起交办时，先完成本次要求的实现或分析及相应验证，再根据实际产出写报告。若任务受阻或部分完成，围绕已取得的证据讲解，并交代受阻点和待验证事项。
- 补写历史阶段时，先确定对应版本、运行批次或历史产物。若当前代码已改动，注明它与历史结果的关系。遵守当次对修改和复跑的限制。
- 小改动抓住一个知识点，给出一个代码入口和一个核对动作。完整实验或算法阶段可加入数据流、前后对照、图表和复现步骤。结合用户已经掌握的知识选择深度。

## 从项目取材

先读本次要求和实际改动，再找最能解释它的入口文件、关键函数、测试、日志或结果表。优先从源文件或原始结果核对报告里的数字，说明对应的版本、工况或运行批次。项目资料缺失时，说明能确认到哪一步。源码支持实现层面的解释，运行数据支持对应条件下的观察。

## 讲清楚一个变化

以下顺序适合大部分任务。小任务可以合并段落。

1. **先讲发生了什么。** 用项目里的一个现象说明为什么要改、修改影响谁。例如，地图里一条捷径更短，拐角处留给平台跟踪的空间也变小了。术语、英文模式名、字段、符号和单位在首次用到时解释。
2. **沿着数据走一遍。** 用「入口 → 关键判断 → 输出」说明改动，指出读者从哪个文件和函数开始。选少量真实代码，解释关键输入、条件、输出以及其中的单位。公式或参数首次出现时，尽量配一组能手算的数值，并说明它改变了哪个实际决策。
3. **展示怎么看结果。** 选一组可追溯的前后对照或一个有代表性的失败案例。交代共同条件、指标和适用范围，保留观察到的失败、回退和性能代价。涉及形状、路线或时间变化时，可用带图例、单位和来源的图。涉及规划与跟踪时，分别解释规划参考线与实际轨迹的指标，注明净空的测量边界和仿真条件。
4. **留一个能独立完成的练习。** 指定要打开的文件、要找的字段或要执行的命令，给出预期结果和通过条件。优先让读者重算一个判断、在回放里定位一个现象，或只变动一个输入来验证自己的预测。教学构造的数据和代码要标明用途。说明命令或示例的实际运行状态。

需要参考讲解粒度时，阅读[示例学习报告](references/example-report.md)。示例中的项目、数据和判断只用于展示写法。

## 交付和核对

- 默认交付简体中文 Markdown，用户指定语言和格式时按当次要求执行。沿用项目已有的报告位置和命名，无约定时用 `docs/<主题>学习报告_<日期>.md`。更新历史报告按用户要求执行，新报告用独立文件名。
- 交付前逐项核对关键数字、代码定位、图表和文件链接，优先用可随仓库迁移的相对路径。把已验证的观察、基于代码的推断和仍待验证的问题写清楚，尤其留意单个案例的结论能支持多大范围。
- 把练习从头走一遍，核对读者能获得所需信息。如果复现需要依赖、数据或初始条件，在步骤旁注明。最终答复附报告路径，概括报告讲了什么和实际做过的验证。
